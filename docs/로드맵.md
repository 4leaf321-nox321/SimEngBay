# 로드맵 — 해석 도메인을 얹는 순서

> 2026-09-20. 공통 틀(로그인 · 부서 · 배포)은 됐고 도메인은 비어 있다. 여기는 **무엇을 어떤
> 순서로** 만드는지와, 그 전에 합의한 아키텍처 결정이다. 결정의 근거는 아래 「결정」 에.

## 전체 흐름

```
오케스트레이터
   │  POST /api/simulations  (JobSpec, PAT 로 인증)
   ▼
API 서버 (이 저장소) ── PostgreSQL(작업 상태 · 산출물 목록) ── filestore(작업 폴더)
   │
   ├─ fetch_geometry   : CAD 플랫폼 → STEP/x_t + topology.json
   ├─ fetch_materials  : 물성 DB → MatML XML
   ├─ build_model      : PyMechanical 워커(Apptainer, 호스트 /ansys_inc bind)
   │      형상 임포트 → 물성 → Named Selection(centroid 매칭) → 접촉 → 메시 → BC → 해석 설정
   │      → WriteInputFile(.dat) + .mechdb(디버깅용)
   ├─ submit_solve     : 기존 솔버 시스템(Linux · Slurm)에 .dat 전달
   ├─ monitor          : 상태 폴링 · 로그 수집
   ├─ extract          : DPF → 고유진동수 JSON · 컨투어 PNG · 표면 메시+스칼라 VTP → filestore
   └─ callback         : 오케스트레이터에 webhook (결과 URL + 요약) · 화면은 폴링
```

## 단계

> 실행 단위로 쪼갠 일감은 [해석-연동-계획.md](해석-연동-계획.md) 에. 여기는 순서와 결정만.

### 1단계 — 작업(job) 뼈대 ✅ 완료 (2026-09-20)

된 것: `app/modules/simulations`(표 · 상태 기계 · 서비스 · 라우터) · `app/core`(스펙 · 단계 ·
실행기, 웹 · DB 를 모른다) · `app/worker.py`(DB 큐) · 화면(목록 · 상세 타임라인 · 새 작업 ·
폴링) · PAT 범위 `simulations:write` · 홈의 「남은 일」 에 실패한 작업 · 부서 참조 · 통폐합 ·
배포 워커 유닛(`<slug>-worker@N`). 실행기는 `fake` 하나 — 상태 기계 · 화면 · API 가 Ansys 없이
검증된다. 시험 백엔드 123 · 프론트 57.

남긴 것: 단계별 재시도(지금은 처음부터 다시) · 작업 취소 · 워커 살아 있는지를 서버 화면에.

- `app/modules/simulations` — `Simulation`(작업) · `SimulationArtifact`(산출물) 표. 상태 기계:
  `queued → fetching → modeling → solving → extracting → done | failed`. 각 단계 시작 · 종료 시각과
  오류 코드(`geometry_import` · `region_unresolved` · `mesh_failed` · `solver_failed` · `license`).
- `app/worker.py` — DB 를 큐로 쓴다(AutoJigGenerator ADR 0003 과 같은 방식: `SELECT … FOR UPDATE SKIP
  LOCKED`). 워커 수 = Mechanical 라이선스 수. `JOBS_INLINE=1` 이면 요청 안에서 돈다(시험).
- JobSpec 스키마(pydantic) — 레시피별(`modal` · `static`)로 허용 칸을 제한한다. Mechanical 의 모든
  기능을 노출하지 않는다.
- 화면: 「해석 작업」 목록 · 상세(단계별 상태 · 로그 · 산출물) · 폴링(`_SKIP` 에 등록).
- PAT 쓰기 범위 `simulations:write` 를 연다.

### 2단계 — FE 모델링 (PyMechanical) ✅ 뼈대 완료 (2026-09-20)

된 것: `app/core/mechanical`(임포트 · 물성 · 메시 · `.dat` · `.mechdb`) · `app/core/solve`(MAPDL
배치) · `app/core/dpf`(고유진동수) · 실행기 `local` · `windows-bridge`. **Ansys 2025 R2 로 확인** —
판 100x60x5 가 2583.1 Hz, L 브래킷이 3315.2 Hz(둘 다 자유-자유, 강체 모드 6개). 실측과 함정은
[해석-연동-계획.md](해석-연동-계획.md) 1.5단계에.

남은 것: 형상 영역 매칭(`topology.json` · Named Selection)과 경계조건 — 지금은 구속을 주면
`region_unresolved` 로 **즉시 실패**한다. 물성 DB · MatML 은 명령 조각(`MP,EX,matid,…`)으로
대신하고 있다.


- `app/core/mechanical/` — 웹 · DB 를 모르는 순수 파이썬. `build(spec, workdir) → ModelResult`.
- 형상 영역 매핑: CAD 서버의 `topology.json`(영역 이름 → 면들의 centroid · 법선 · 면적)을
  `GeometryData` 면 순회로 허용오차 매칭 → Named Selection. **실패하면 모델링 단계에서 즉시 실패**시킨다.
- 물성: 물성 DB → MatML 3.1 XML 생성기 → `Model.Materials.Import`.
- 워커 컨테이너: `deploy/worker.def` — ubuntu:24.04 + X 라이브러리 + xvfb + venv(PyMechanical · DPF ·
  PyVista/OSMesa). Ansys 는 `--bind /shared/ansys_inc:/ansys_inc`. `mechanical-env` 로 실행.
  프로세스당 `App` 1개, `app.new()` 로 순환, N건마다 재시작.
- 첫 PoC: CAD 생성기가 준 STEP 하나 → 면 순회 → 메시 → `.dat` → 기존 솔버 → DPF 고유진동수.

### 3단계 — 결과 추출 · 뷰어 (DPF) ✅ 완료 (2026-09-20)

된 것: `core/dpf`(고유진동수 · 표면 메시 VTP · 썸네일 PNG · `solve.out` 의 유효질량비) ·
`GET /simulations/{id}/result` · 화면(표 + 막대 + 썸네일 + `shared/viewer` 의 vtk.js 뷰어,
`lazy()`). 실측과 함정은 [해석-연동-계획.md](해석-연동-계획.md) 3단계에.

남은 것: 모드 비교 화면 · 변위 배율 조절 · 리눅스 워커의 OSMesa 확인.


- `app/core/dpf/` — `.rst` → 고유진동수(+ `.out` 참여계수 파싱) JSON, 표면 메시(skin · 중간절점 제거
  · decimation) + 스칼라 → VTP/glTF, PyVista offscreen PNG.
- 화면: 고유진동수 표 + 막대(`shared/charts`), 컨투어 썸네일, `shared/viewer`(vtk.js, `lazy()`) —
  회전 · 컬러바 · 모드형상 애니메이션(노드 변위 벡터).
- 응답 메타데이터에 단위계 · 정규화 방식을 반드시 넣는다.

### 4단계 — 영역 매칭 · 구속 모달 ✅ 완료 (2026-09-23)

CompCore 가 `topology.json`(영역의 좌표 지문)을 내고, 이쪽이 그 좌표로 형상에서 면을 다시 찾아
Named Selection · Fixed Support 를 건다(`core/regions`). **볼트 구멍 넷을 고정한 L 브래킷이
1,519 Hz · 강체 모드 0개**, 유효질량비가 실값을 갖는다. 평면과 원통을 다르게 재는 이유(반쪽
구멍)와 함정은 [해석-연동-계획.md](해석-연동-계획.md) 4단계에.

### 5단계 — 오케스트레이션 연동

- CAD 플랫폼 · 물성 DB 클라이언트(`app/shared/clients/`), 입력 해시 멱등성(같은 스펙이면 캐시 히트),
  단계별 재시도(솔버만 실패하면 모델링 다시 안 함), webhook 콜백(서명 · 재시도).
- 필요해지면 Prefect/Temporal 로 갈아탄다 — 단계가 늘고 「솔버 3시간 대기 중 워커 사망 복구」 가
  DB 큐만으로 지저분해질 때.

### 그 뒤

- 해석용 MCP 서버(AI 가 해석을 건다) — `deploy.sh` 의 MCP 자리를 쓴다.
- DOE(AutoJigGenerator 의 것과 연결) · 결과 비교 화면.

## 결정

| 물음 | 결정 | 이유 |
| --- | --- | --- |
| OS | **전부 리눅스.** 개발자 Windows PC 는 `.mechdb` 를 GUI 로 여는 디버깅용 | CAD · 솔버가 이미 리눅스. 형상 편집(SpaceClaim) · Workbench 가 파이프라인에 없다. `.mechdb` 는 OS 간 호환 |
| 컨테이너 | Apptainer, Ansys 는 호스트 bind | Docker 미사용 환경. 이미지가 수십 GB 가 되는 것을 피한다. 읽기 전용 루트 · 홈 상속은 `--bind` · `--cleanenv` 로 |
| Ansys 버전 | 2024R2 이상 고정 | 리눅스 임베디드는 2023R2 부터지만 안정성은 2024R2 부터. 개발 PC 와 같은 버전 |
| 모델링 워커의 역할 | `.dat` 생성까지만. 솔브는 안 한다 | Mechanical 이 솔브 동안 라이선스를 물고 있게 되고 HPC 분산이 안 된다 |
| 결과 추출 | DPF 로 단일화. Mechanical 의 `ExportImage` 는 안 쓴다 | `.rst` 만 있으면 되고 Mechanical 라이선스 · 디스플레이가 필요 없다 |
| 뷰어 | 추출 시점에 PNG + VTP 를 만들어 정적으로 서빙, 브라우저 vtk.js | trame 같은 서버 세션 방식은 사용자당 서버 상태가 생긴다 |
| 형상 영역 | CAD 쪽 `topology.json` + centroid 매칭. 속성 기반 Named Selection 임포트는 보조 | STEP 은 면 이름을 안정적으로 못 나른다. OS 문제가 아니라 포맷 문제 |
| CAD 와의 계약 | 하중 · 구속 면은 CAD 가 미리 분할, 형상 수리 · 미드서피스도 CAD 책임 | 리눅스 Mechanical 에는 형상 편집기가 없다. 이 계약이 안 지켜지면 그때 모델링 워커만 Windows 로 |
| 개발 라이선스 | Student 는 Windows 전용 · 비상업. 기존 라이선스 서버를 개발 PC 에서 바라본다 | 기술적으로는 Student 로 개발되지만 약관 문제 |
| 큐 | DB 를 큐로(1단계). 워크플로 엔진은 필요해질 때 | AutoJigGenerator 에서 검증된 방식. 처음부터 Temporal 은 과하다 |

## 리스크 (PoC 로 먼저 확인)

1. 리눅스 Mechanical 임베디드에서 CAD 서버의 STEP/x_t 가 문제없이 임포트되고 `GeometryData` 면 순회가 되는가.
2. 파라미터를 바꾼 형상 여러 개에 대해 centroid 매칭이 안정적으로 Named Selection 을 잡는가.
3. 보유 라이선스(Mechanical Enterprise · 솔버 · HPC)로 동시에 몇 개 워커 · 솔브가 가능한가.
