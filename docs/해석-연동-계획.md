# 해석 연동 계획 — AutoJigGenerator 형상을 받아 모달 해석까지

> 작성 2026-09-20. [로드맵](로드맵.md) 의 단계를 **실행 단위**로 쪼갠 것이다. 무엇을 만들고, 무엇이
> 되면 끝인지, 무엇을 먼저 확인해야 하는지를 적는다. 로드맵은 「순서와 결정」, 이 문서는 「일감」.
> 진행하면서 바뀐 것은 여기 고친다.

## 0. 지금 상태

| 저장소 | 있는 것 | 없는 것 |
| --- | --- | --- |
| SimEngBay | 로그인 · PAT · 부서 · 첨부 · 배포 (공통 틀) | 도메인 모듈 0개. `app/core` · `app/worker.py` 없음 |
| AutoJigGenerator | 레시피 CAD · 지그 생성(bolted · bending · drop) · DOE 내보내기 | **해석**. 결과가 들어갈 자리(`DoePoint.metrics`, `/filter` · `/tradeoff`)만 비워 둠 |

### AutoJigGenerator 가 실제로 내주는 것

| 경로 | 내용 | 쓰임 |
| --- | --- | --- |
| DOE 공유 폴더 `DOE_EXPORT_ROOT/<이름>-<id8>/` | `manifest.csv` · `study.json` · `README.txt` · `points/pNNNN.step` | **해석이 읽으라고 만든 계약.** CSV 에 "해석 결과 열은 해석이 붙인다" 고 명시 |
| `GET /api/doe/{id}` · `/manifest.csv` · `/points/{n}/mesh` | 스터디 · 설계점 메타 | PAT 로 붙는다 |
| `GET /api/parts/{id}/versions` · `GET /api/artifacts/{id}/download` | 승격된 부품 · 지그의 불변 버전 STEP | 단건 해석 |
| `DoePoint.metrics` (JSONB) | 비어 있음 | 우리 결과가 들어갈 자리. **쓰는 API 는 아직 없다** |

**없는 것: `topology.json`.** 로드맵은 「CAD 가 영역 이름 → 면 centroid · 법선 · 면적을 준다」 를
전제하는데 AutoJig 에 그 내보내기가 없다. 재료는 있다 — `core/recipe/digest.py` 가 면마다 법선 ·
면적 · 중심을 이미 계산하고, 지그 생성기는 고정면 · 볼트 구멍 · 롤러 접촉면을 **알고 있으면서
STEP 에 이름을 못 나를 뿐**이다.

## 1. 기술 스택

| 층 | 있음 | 새로 얹는 것 |
| --- | --- | --- |
| API | FastAPI · SQLAlchemy 2 · Alembic · PostgreSQL 16 · PAT | `modules/simulations` · `app/worker.py` (DB 큐, `FOR UPDATE SKIP LOCKED`) |
| 코어(순수 파이썬) | — | `app/core/mechanical` (PyMechanical 임베디드) · `app/core/dpf` (PyDPF) · `app/core/matml` · `app/core/regions` (centroid 매칭) |
| 워커 컨테이너 | Apptainer 틀 | `deploy/worker.def` — ubuntu:24.04 + xvfb + venv, 호스트 `/ansys_inc` bind, `mechanical-env` |
| 솔브 | — | 기존 리눅스 솔버(Slurm)에 `.dat` 제출 · 폴링. 어댑터로 두어 로컬 직접 실행과 갈아끼운다 |
| 후처리 | — | DPF → JSON · PNG(PyVista/OSMesa) · VTP(skin · decimation) |
| 프론트 | React 19 · Vite · Tailwind 4 · shadcn · `shared/charts` | `modules/simulations` 화면 · `shared/viewer` (vtk.js, `lazy()`) |
| 외부 연동 | PAT | `shared/clients/autojig.py` + DOE 공유 폴더 읽기 · webhook 콜백 |

`core` 는 `fastapi` · `sqlalchemy` · `app.modules` · `app.shared` 를 import 하지 않는다(AGENTS.md).
모델링 스크립트는 서버 없이 `python -m app.core.mechanical.build spec.json workdir/` 로 돈다.

## 2. 단계

```
1  작업 뼈대 ──▶ 1.5  자유-자유 모달 PoC ──▶ 2  솔브 제출 ──▶ 3  DPF · 뷰어
                      (topology 없이)              │
0  CAD 계약 (AutoJig 쪽) ───────────────────────────┴──▶ 4  영역 매칭 · 고정 모달 ──▶ 5  DOE 연동
```

0단계는 AutoJig 저장소의 일이고 1 · 1.5 · 2 · 3 과 **독립**이다. 4단계에 가서야 필요하다.

### 1단계 — 작업(job) 뼈대 ✅ 완료 (2026-09-20)

왜 먼저: 해석 · 결과 추출 · DOE 배치가 전부 「작업」 이다. 이게 없으면 기능마다 실행 · 상태 · 목록을
따로 만든다. AutoJigGenerator 1단계와 같은 이유, 같은 방식.

- `app/modules/simulations` — `Simulation` · `SimulationArtifact` 표.
  - 상태: `queued → fetching → modeling → solving → extracting → done | failed`. 단계마다 시작 ·
    종료 시각. 오류 코드는 `errors.code("SIM", n)` 로만 — `geometry_import` · `region_unresolved` ·
    `mesh_failed` · `solver_failed` · `license` · `timeout`.
  - `JobSpec`(pydantic) — 레시피별로 허용 칸을 제한한다. 처음은 `modal` 하나.
    ```
    recipe: modal
    source: { kind: upload | part_version | doe_point, ... }
    material: { name, E, nu, rho }            # 물성 DB 가 붙기 전엔 직접 준다
    mesh: { element_size_mm?, order: quadratic }
    modes: 10
    constraints: []                            # 비면 자유-자유. 4단계부터 영역 이름이 온다
    ```
  - 산출물: `input.step` · `spec.json` · `model.mechdb` · `model.dat` · `solve.out` · `model.rst` ·
    `result.json` · `mode_NN.png` · `mode_NN.vtp`. 전부 `filestore/simulations/<id>/`.
- `app/worker.py` — DB 를 큐로. `JOBS_INLINE=1` 이면 요청 안에서 돈다(시험). `run.py` 가 자식으로
  띄운다. 워커 수 = Mechanical 라이선스 수(`.env` `WORKER_COUNT`).
- 단계 실행기는 **가짜(fake) 백엔드**를 먼저 둔다 — 각 단계가 sleep 하고 빈 산출물을 만든다.
  시험은 이것으로 돈다. Ansys 없는 CI 에서 상태 기계 · 화면 · API 가 전부 검증된다.
- PAT 쓰기 범위 `simulations:write` — `register_write_scope("/api/simulations", …)`.
- 화면: 「해석 작업」 목록(상태 · 레시피 · 출처 · 걸린 시간) · 상세(단계 타임라인 · 로그 · 산출물
  내려받기) · 새 작업(STEP 올리기 + 물성 + 모드 수). 폴링은 `_SKIP` 에 등록. 사이드바 · 부서 홈
  레지스트리에 붙인다.
- **완료 기준**: STEP 을 올려 `POST /api/simulations` 하면 큐에 들어가고, 가짜 워커로 상태가 끝까지
  흘러 화면 타임라인에 보인다. PAT 로 같은 일을 curl 로 한다. 시험은 Ansys 없이 돈다.

**된 것**(2026-09-20): 위 전부. 더한 것 — 실행기 레지스트리(`app/core/executors`, 설정 오타는
워커 기동에서 죽는다) · `heartbeat_at` 으로 갇힌 작업 되살리기(솔브가 몇 시간이라 `started_at`
만으로는 「죽었나 오래 걸리나」 를 못 가른다) · 실패 코드 ↔ 화면 이름표를 대조하는 구조 시험 ·
배포 워커 유닛(`<slug>-worker@N`, `WORKER_COUNT`).

**남긴 것**: 단계별 재시도(지금은 처음부터 다시 — 5단계에서 `.dat` 재사용) · 작업 취소 ·
워커가 살아 있는지를 서버 화면에 · 입력 해시 멱등성(5단계).

### 1.5단계 — 자유-자유 모달 PoC (topology 없이) ✅ 완료 (2026-09-20)

왜 여기서: 자유-자유 모달은 **구속이 없다**. Named Selection · 경계조건 단계가 통째로 빠지고 나머지
(STEP 임포트 → 물성 → 접촉 → 메시 → `.dat` → 솔브 → DPF)는 최종 파이프라인과 **같은 코드**다.
로드맵 리스크 1(리눅스 임베디드에서 AutoJig STEP 임포트)과 3(라이선스 · 동시 워커 수)을 topology
계약 없이 먼저 확인한다. AutoJig 의 `core/vibration.py` 가 닫힌 식으로 「가늠값」 만 내는 자리에
진짜 값이 처음 붙는 순간이기도 하다.

- `app/core/mechanical/build.py` — `build(spec, workdir) → ModelResult`. 프로세스당 `App` 1개,
  `app.new()` 로 순환, N 건마다 재시작.
  1. `geometry_import`: STEP → `Model.GeometryImportGroup.AddGeometryImport`. 바디 수 · 면 수를 로그.
  2. `material`: `spec.material` → MatML 3.1 XML(`core/matml.py`, 순수) → `Model.Materials.Import`
     → 모든 바디에 할당.
  3. `contact`: 다중 바디면 자동 접촉 감지 그대로(bonded). 손대지 않는다.
  4. `mesh`: 요소 크기(없으면 Mechanical 기본) · 2차 요소. 실패는 `mesh_failed`.
  5. `analysis`: Modal, `MaximumModesToFind = spec.modes + 6`. **구속 없음.**
  6. `WriteInputFile(model.dat)` + `SaveAs(model.mechdb)`(디버깅용 — Windows GUI 에서 연다).
- 강체 모드 처리: DPF 결과에서 앞 6개(≈0 Hz, 임계 1 Hz)를 `rigid_body` 로 표시하고 탄성 모드부터
  번호를 매긴다. `result.json` 에 `{ "boundary": "free-free", "rigid_body_modes": 6, ... }`.
- 워커 컨테이너 `deploy/worker.def` + `deploy.sh` 의 워커 유닛. 개발 PC(WSL)에서 라이선스 서버가
  보이면 컨테이너 없이 venv 로 먼저.
- 시험 픽스처: AutoJig 가 만든 STEP 셋 — 기본 판 · 구멍 뚫린 L 브래킷 · `bolted` 지그+제품(다중
  바디). `tests/fixtures/step/`.
- **완료 기준**: 세 STEP 이 임베디드 Mechanical 에서 임포트 · 메시 · `.dat` 까지 간다 — 개발 PC(Windows 다리)에서, 그리고 서버(리눅스 `local`)에서 한 번.
  `.dat` 를 솔버에 손으로 넣어 `.rst` 를 얻고 DPF 로 고유진동수를 읽는다(3단계의 앞당긴 조각). L
  브래킷의 첫 탄성 모드가 손계산 · AutoJig 가늠값과 자릿수가 맞는다.
- **안 되면**: 임베디드 임포트가 AutoJig STEP 을 못 읽으면 x_t(Parasolid) 내보내기를 AutoJig 에
  요청하거나, 모델링 워커만 Windows 로 — 로드맵이 예약해 둔 분기.

**된 것**(2026-09-20, Ansys **2025 R2**(v252) Student · Windows): 네 단계가 끝까지 돈다. 손으로
확인한 순서 그대로 코드가 되었다 — `app/core/mechanical`(임포트 · 물성 · 메시 · `.dat` · `.mechdb`) ·
`app/core/solve`(MAPDL 배치) · `app/core/dpf`(고유진동수 · 메시 · 단위계) · `app/core/run.py`(단계
하나를 다른 프로세스에서) · `local` · `windows-bridge` 실행기. 시험은 `tests/ansys/`(표시 `ansys`,
기본으로 안 돈다)와 Ansys 없이 도는 실행기 단위 시험.

| 형상 | 절점 | 강체 모드 | 1차 탄성 | 모델링 | 솔브 | 추출 |
| --- | --- | --- | --- | --- | --- | --- |
| 판 100x60x5 (요소 8mm) | 836 | 6 | **2583.1 Hz** | 51초 | 19초 | 2초 |
| L 브래킷 + 구멍 (6mm) | 1,976 | 6 | **3315.2 Hz** | 52초 | 19초 | 2초 |

형상은 AutoJigGenerator 와 같은 도구(build123d/OpenCascade)로 만들었다 — **리스크 1 해소**:
그 STEP 이 임베디드 Mechanical 에 그대로 들어오고 면 순회 · 메시가 된다. 솔버 출력의 표와 DPF 가
읽은 값이 같았다.

**실측으로 정한 것**(전부 코드 주석에 근거와 함께 있다):
- **계획은 2024R2 였지만 깔려 있는 것은 2025 R2**다. 임베디드 · 솔버 · DPF 가 다 됐으므로 그대로
  간다(`ANSYS_VERSION=252`). 운영 서버의 버전이 다르면 이 값만 바꾼다.
- **물성은 MatML 대신 명령 조각**으로 준다(`MP,EX,matid,…`). MatML 은 한 칸이 틀려도 「임포트는
  됐는데 값이 안 들어간」 상태가 되고, 그것은 고유진동수가 틀린 뒤에야 드러난다.
- **단위계를 확인하고 쓴다.** 명령 조각의 숫자에는 단위가 없다 — MKS 가 아니면 세우지 않는다.
- **WSL → Windows 로는 환경변수가 안 건너간다**(WSLENV 에 적은 것만). `PYTHONPATH` 를 주고
  띄운 Windows 파이썬에서 그 값이 `None` 이었다 — 그래서 경로를 **명령줄에** 싣는다.
- **자식의 stdout 은 UTF-8 로 고정한다**(`-X utf8`). 한국어 Windows 는 cp949 로 찍고, 그것을
  UTF-8 로 읽던 부모가 `UnicodeDecodeError` 로 죽었다 — 단계는 성공했는데 워커가 터진다.
- **강체 모드 수를 세어 경고한다.** 자유-자유인데 6개가 아니면 접촉이 안 잡힌 것이다(리스크 4).

**남긴 것**: 리눅스 `local` 실행기로 서버에서 한 번 돌려 보기(워커 유닛에 `/ansys_inc` bind 자리는
만들어 두었다) · Slurm 어댑터(2단계) · 모드 형상 PNG · VTP 와 뷰어(3단계) · 구속(4단계 — 지금은
`region_unresolved` 로 **즉시 실패**한다).

### 2단계 — 솔브 제출 · 감시

- `app/core/solve/` — `SolverAdapter` 인터페이스: `submit(dat, workdir) → handle` · `status(handle)` ·
  `collect(handle) → (rst, out)`. 구현 둘:
  - `local`: `ansys -b -i model.dat -o solve.out` 을 subprocess 로(개발 · PoC).
  - `slurm`: `sbatch` 스크립트 생성 · `squeue`/`sacct` 폴링 · 공유 폴더에서 회수. 큐 · 파티션 ·
    코어 수는 `.env`.
- 워커의 `solving` 단계는 **기다리지 않는다** — 제출하고 handle 을 저장한 뒤 다음 작업을 잡는다.
  별도 루프가 `solving` 상태를 폴링한다(워커 사망해도 handle 로 되찾는다).
- `.out` 에서 라이선스 오류 · 수렴 실패 · 메모리 부족을 오류 코드로 구분. 타임아웃은 레시피별 기본값.
- **완료 기준**: 1.5 의 `.dat` 가 손 없이 솔버로 가서 `.rst` 가 filestore 에 돌아온다. 워커를 죽였다
  살려도 `solving` 작업이 끝까지 간다.

### 3단계 — 결과 추출 · 뷰어 (DPF) ✅ 완료 (2026-09-20)

- `app/core/dpf/extract.py` — `.rst` → `result.json`(모드 번호 · Hz · 강체 여부 · `.out` 에서 참여계수
  · 유효질량비), 모드별 표면 메시(skin · 중간절점 제거 · decimation) + 변위 스칼라 → VTP, PyVista
  오프스크린 PNG(등각 뷰, 컬러바). 단위계(`mm-t-s` / `SI`) · 변위 정규화 방식(질량 정규화 등)을
  메타에 반드시 넣는다.
- 화면: 상세에 고유진동수 표 + 막대(`shared/charts`) · 모드 썸네일 격자 · `shared/viewer`(vtk.js,
  `lazy()`) — 회전 · 컬러바 · 모드형상 애니메이션(절점 변위 벡터를 sin 으로 흔든다).
- **완료 기준**: 작업 상세에서 10개 모드의 Hz 와 형상을 브라우저에서 본다. 뷰어 번들은 결과를 안
  보는 화면의 첫 로드에 안 실린다(빌드 크기 시험).

**된 것**(2026-09-20): `core/dpf/shapes.py`(표면 → 중간 절점 제거 → 삼각형 → 솎기 → VTP,
PyVista 오프스크린 PNG) · `core/dpf/participation.py`(`solve.out` 의 유효질량비) · 결과 요약
API(`GET /simulations/{id}/result` — **DB 에 옮겨 담지 않는다**, 해석이 낸 파일이 정본) ·
화면(고유진동수 표 + 막대 · 모드 썸네일 · `shared/viewer`(vtk.js) 회전 · 컬러바 · 모드 형상
애니메이션).

| 값 | 실측 |
| --- | --- |
| L 브래킷 모드 하나의 VTP | 13 KB (표면 · 삼각형 · 변위 + 크기 배열) |
| 썸네일 PNG | 27~34 KB (480x360, 원형을 옅게 겹친다) |
| 뷰어 청크 | vtk.js 조각들 ≈ 200 KB(gz) — **첫 로드에 안 실린다**(`lazy()`) |
| 추출 단계 시간 | 2초 → 모드 형상 다섯 장까지 포함해 ~10초 |

**실측으로 정한 것**:
- **변위 필드의 순서는 메시 절점 순서와 다르다**(메시는 1·2·3…, 필드는 1·137·129…). 순서대로
  붙이면 뒤죽박죽인 모양이 나오는데 **그것은 「이상한 모드 형상」 으로 보일 뿐 오류가 아니다.**
  절점 번호로 맞춘다.
- **작은 모델은 솎지 않는다.** 78점짜리를 더 줄이면 모양이 사라진다(면 20,000 이상만 솎는다).
- **VTP 는 바이너리로 쓴다** — ASCII 는 두 배(7.8KB / 14.6KB)고 vtk.js 가 둘 다 읽는다.
  그 계약은 프론트 시험(`shared/viewer/MeshViewer.test.ts`)이 **진짜 산출물 한 장**으로 지킨다.
- **썸네일은 변위를 과장해 그린다**(모델 크기의 15%). 모달의 변위는 질량 정규화된 상대값이라
  실제 크기로 그리면 아무것도 안 움직인 그림이 나온다. 화면도 같은 이유로 `sin(t)` 로 흔든다.
- **참여계수 표는 제목과 첫 줄 사이에 글자 줄이 둘 있다.** 「숫자 줄이 아니면 표가 끝났다」 로
  읽으면 표를 시작하자마자 놓친다(그렇게 만들었다가 빈 결과를 받았다).
- 자유-자유에서는 **강체 모드가 유효질량을 전부 가져간다** — 탄성 모드의 참여계수가 0 이다.
  이 값이 쓸모를 갖는 것은 구속이 붙는 4단계부터다.

**그림을 고르게 했다(2026-09-21)**: 모드 번호를 가로축에 둔 막대는 정의상 **단조 증가하는
계단**이라 모델마다 모양이 같고, 그 물음에는 표가 더 잘 답한다. 진동에서 묻는 것은 대역이다 —
그래서 기본을 **스펙트럼**(가로축 주파수 · 높이 유효질량비)으로 바꾸고 셋 사이를 오가게 했다.

| 그림 | 답하는 물음 |
| --- | --- |
| 스펙트럼(기본) | 어느 **대역**에 모드가 몰려 있나 · 가진 대역 안에 무엇이 있나 |
| 누적 유효질량 | 몇 Hz 까지 봐야 질량의 90%를 잡나 = **모드 수가 충분한가** |
| 모드별 막대 | 몇 번째가 몇 Hz 인가(표와 같은 물음 — 익숙한 사람을 위해 남겼다) |

- **자유-자유에서는 유효질량비가 전부 0 이다**(강체 모드가 다 가져간다). 스펙트럼은 줄기를
  균일한 높이로 세우고 이유를 적고, 누적 그림은 **탭이 잠기며 왜 잠겼는지 말한다** — 눌러 보고
  빈 그림을 만나게 하지 않는다. 이 그림들이 제값을 하는 것은 구속이 붙는 4단계부터다.
- 줄기는 `ReferenceLine segment` 로 그린다. 막대를 수치 축에 얹으면 자리 잡는 규칙이 축 종류에
  따라 달라지는데, 선분은 「이 x 에서 0 부터 y 까지」 라고 적은 그대로 선다.
- 모드 300개가 넘으면 줄기를 생략하고 점만 남긴다(겹쳐서 검은 띠가 될 뿐이다).
- **표는 20개씩 쪽으로 나눈다.** 모달은 모드 수십 개가 흔하다. 스펙트럼에서 고른 모드가 다른
  쪽에 있으면 그 쪽으로 넘어간다 — 안 그러면 눌러도 아무 일도 안 일어난 것처럼 보인다.

**자유-자유를 설명하는 말을 만들었다(2026-09-21)**: 유효질량비는 구속이 없으면 **정확히 0** 이다
(탄성 모드가 강체 모드와 질량 직교 — 공중에 뜬 물체를 균일하게 밀면 변형하지 않는다). 그래서
변위장 자체에서 읽는 두 지표를 모든 모드에 붙인다(`core/dpf/metrics.py`, **순수 파이썬** — numpy 는
워커에만 있어서 그것을 쓰면 이 수학을 CI 에서 시험할 수 없다):

| 지표 | 뜻 | L 브래킷 실측 |
| --- | --- | --- |
| `direction_share` | 축별 변위 에너지 비중 — 「주로 어느 축으로 움직이나」 | 7번 X 0.54 · 9번 Z 0.93 |
| `localization` | 참여비(IPR). 1 = 전체가 함께, 0 에 가까울수록 한 구석만 | 0.17~0.38 |

- **비율만 쓴다.** 모달 변위는 질량 정규화된 상대값이라 크기에는 뜻이 없다 — 전체를 10배 해도
  두 지표는 그대로다(시험이 지킨다).
- **임계값을 실측으로 낮췄다**(0.3 → 0.1). 판 전체가 반파장으로 휘기만 해도 참여비가 0.67 이고,
  몸통의 3분의 1이 움직이는 정상 모드가 0.17~0.38 이었다. 0.3 으로 두면 **정상 모드에 매번
  「국부」 경고가 붙고, 그러면 그 경고는 아무 뜻도 못 갖는다.** 립 하나가 떠는 모드는 0.05 아래다.
- 화면은 판정과 **숫자를 함께** 보여 준다 — 경계가 하나인 판정이라 경계 근처는 숫자를 봐야 한다.
- 뷰어: 화면 높이에 맞춘 크기 · **전체 화면** · **변위 배율 슬라이더**(얇은 판과 두꺼운 블록은
  적정 배율이 다르다) · `ResizeObserver`(창은 그대로인데 상자만 바뀌면 캔버스가 옛 크기로 남는다).

**남긴 것**: 가진 대역 입력(스펙에 칸 하나 — `Spectrum` 은 이미 띠를 그릴 수 있다) · 여러 모드를
나란히 보는 비교 화면 · 변위 배율을 사람이 조절하는 칸 · 두 해석의 모드 상관(MAC) ·
리눅스 워커의 OSMesa(`vtk-osmesa`) 확인 — PNG 만 그것에 걸리고 VTP · 고유진동수는 무관하다.

  찾게 하지 않는다(CompCore 가 그 열을 만든 이유와 같다).
- 화면: 「DOE 가져오기」 — 폴더 경로를 주면 **먼저 미리보기**(점 몇 개 · 변수 무엇 · 건너뛸 것
  몇 개)를 보이고, 누르면 N 개가 걸린다.

| p0002 | 12 | 1,651 Hz | 1.185 kg |
| p0003 | 20 | 1,713 Hz | 1.773 kg |

「두께를 20 까지 올려도 1차는 1,713 Hz 에서 더 안 오르는데 질량은 2.4배가 된다」 — 이것이
설계점을 고르는 일이고, CompCore 가 넘긴 자리다.

- **질량이 두 번째 축이다.** 지그는 가볍고 단단해야 하므로 축 하나로는 고를 수 없다. 모델링
  단계가 Mechanical 의 바디 부피(활성 단위계에서 m³) x 밀도로 낸다 — 못 읽으면 `None` 이고
  **틀린 질량은 맞는 침묵보다 나쁘다.**
- **스터디를 따로 저장하지 않는다.** 작업 표의 `source_meta` 에서 모은다 — 스터디 표를 두면
  작업을 지웠을 때 둘이 어긋나고, 그때 어느 쪽이 맞는지 알 방법이 없다.
- **축을 사람이 고른다.** 변수도 결과(1~5차 · 질량)도 여럿이라 「무엇 대 무엇」 이 하나로
  정해지지 않는다.
- **아직 안 끝난 점은 안 끝난 대로 보인다.** DOE 하나가 다 도는 데 점 수 x 1~2분이 걸린다 —
  다 끝나야 보여 주면 그동안 아무것도 못 본다. 결과가 없는 점은 **그림에서 빠진다**(0 으로
  그리면 「두꺼울수록 0 에 가까워진다」 는 거짓말이 된다).
- **같은 폴더를 두 번 가져와도 두 벌이 안 생긴다.** 경로를 다시 붙여넣는 일은 흔하고, 그때
  조용히 두 벌이 돌면 라이선스를 두 번 태운다. 이미 가져온 점은 이유와 함께 건너뛴다.

**한 장으로 다시 짰다(2026-09-24)**: 처음에는 「가로축 · 세로축을 고르면 그림 하나」 였는데,
**모드를 하나씩 눌러 봐야 아는 화면은 「전반적으로 어떤가」 에 답하지 못했다**(쓰면서 드러났다).
사람이 묻는 순서대로 네 조각을 한 장에 놓는다:

| 조각 | 답하는 물음 | 실측(브래킷 두께 훑기) |
| --- | --- | --- |
| 한 줄 요약 | 무엇을 얼마나 바꿨더니 무엇이 얼마나 변했나 | 두께 6 → 20, 1차 **+28%**, 질량 **+139%** |
| 모드 지도 | 어느 모드가 빨리 오르고 어디서 엇갈리나 | 2차 1,698 → 5,284 · 4차 3,045 → 3,374 |
| 트레이드오프 | 무겁고 단단함의 흥정. **고를 후보는 어느 것인가** | 파레토 점을 표에 「후보」 로 |
| 행렬 | 값을 집어 가는 자리 | 모드 x 설계점, 못 이은 자리는 **빈칸** |

- **모드 지도가 핵심이다.** 선 하나가 추적된 모드 하나라, 4차가 거의 안 오르는 것(3,045 →
  3,374)과 2차 · 3차가 두 배 넘게 오르는 것이 한눈에 보인다 — 예전 화면에서는 모드를 다섯 번
  눌러야 알 수 있었다.
- **파레토를 짚어 준다.** 주파수는 높을수록 · 질량은 낮을수록 좋으니, 더 낫지도 가볍지도 않은
  점은 고를 이유가 없다. 남는 것에 「후보」 를 단다.
- **못 이은 자리는 빈칸이다.** 숫자를 채우면 그 값이 같은 모드로 읽힌다(5 · 6차가 그랬다).

**남긴 것**: 목표 주파수 대비 여유(가진 대역을 받으면) · 스터디 여럿을 겹쳐 보기 ·
변수 둘 이상일 때의 면 보기(지금은 가로축을 고른다).


- 스터디로 묶인 작업들을 한 화면에: **바꾼 변수 vs 결과**(1차 탄성 · 모드별 Hz · 유효질량비).
  산점도(`Spectrum` 의 수치 축을 그대로 쓴다) · 표 · 파레토.
- 「두께 6 · 8 · 10 중 1차 공진이 가장 높은 것」 이 한눈에. **이것이 CompCore 가 넘긴 일이다.**
- 아직 안 끝난 점은 안 끝난 대로 보인다 — DOE 하나가 다 도는 데 N x 1분 걸린다.

#### 그 밖에 — 모드 추적 · 취소 · 정리 ✅ 완료 (2026-09-24)

**① 모드 추적** — 비교 화면이 「1차 · 2차」 를 순번으로 견주면 **조용히 틀린다.** 치수가 바뀌면
모드 순서가 뒤바뀌기 때문이다(mode crossing). 실측으로 실제 그랬다:

| 기준(t=6) | t=12 | t=20 | MAC |
| --- | --- | --- | --- |
| 2차 1,698 Hz | **3번** 3,613 Hz | **3번** 5,284 Hz | 0.99 / 0.95 |
| 4차 3,045 Hz | **2번** 3,313 Hz | **2번** 3,374 Hz | 0.99 / 0.92 |

2차와 4차가 자리를 바꿨다 — 순번으로 이었으면 「2차 대 두께」 가 **두 모드를 섞어 이은 선**이다.

- 모드를 잇는 정본은 주파수가 아니라 **형상**이다. MAC(`core/modes`)으로 잇는다.
- 설계점마다 메시가 달라 절점끼리 못 견준다 → **경계상자를 정규화한 격자**에서 변위를 뽑아
  지문으로 싣는다(`core/dpf/signature.py`, 모드당 192개 실수). 만드는 데는 메시가 필요하고
  그것은 워커에만 있으니 **만들 때 한 번** 뽑고, 잇는 계산은 서버가 지문만으로 한다.
- **못 이으면 잇지 않는다.** MAC 0.6 아래는 비우고 「N 개 설계점에서 못 찾았다」 고 말한다 —
  실측에서 5 · 6차가 그랬다(0.6 · 0.36). 억지로 이은 선은 없는 그림보다 나쁘다.
- 변위 필드의 순서가 메시 절점 순서와 다른 문제(1.5단계의 그 함정)를 `core/dpf/fields.py`
  한 곳으로 모았다 — 지문이 조용히 틀리면 **모드를 엉뚱하게 잇는다.**

**② 작업 취소** — 200점을 잘못 걸면 몇 시간을 라이선스와 함께 태운다. 워커는 다른 프로세스라
DB 칸(`cancel_requested_at`)으로만 알 수 있고, **자식을 기다리는 동안에도 2초마다 본다** —
그냥 기다리게 두면 솔브 세 시간 동안 취소가 아무 일도 안 한다. 실측: 모델링 중에 눌러
**1초 만에** 멈췄다(Mechanical 자식을 terminate → 안 죽으면 kill). 취소는 **실패가 아니다** —
「남은 일」 에 안 오르고 실패로 세지도 않는다. 다시 걸 때 표시를 지운다(안 지우면 첫 확인에서
곧바로 멈춘다).

**③ 작업 정리** — 한 건이 수십 MB 다(`.mechdb` 4.8MB · `.rst` · MAPDL scratch). 실측: DOE 3점을
정리해 **45개 파일 · 13.8MB** 를 줄였고 결과(고유진동수 · 모드 형상 · 추적)는 그대로였다.
서버 화면에 「작업 폴더(MB)」 가 뜬다. **`.rst` 를 지우면 모드를 더 뽑을 수 없으므로** 자동으로
돌지 않고 사람이 누른다. 지운 파일의 **행도 함께 지운다** — 「DB 에는 있는데 파일이 없는」
상태는 백업이 잘못된 것과 구별되지 않는다.

## 3.1 개발 환경 — 실행기(executor)를 갈아끼운다

`core` 는 CLI 다(`python -m app.core.mechanical.build spec.json workdir/`). 워커는 「작업을 잡고 ·
작업 폴더를 만들고 · 그 명령을 실행하고 · 산출물을 등록」 만 하므로, **명령을 어디서 실행하느냐**만
설정으로 갈린다. 코드는 한 벌.

```
WSL                                          Windows
API · PostgreSQL · worker.py                 Ansys 2025 R2(v252) + venv(PyMechanical · DPF)
   │ 단계마다 자식 프로세스 하나                    ▲
   └─ C:\simengbay\venv\Scripts\python.exe -X utf8 -c "sys.path.insert(0, <backend>);
        app.core.run.main()"  <단계> <작업폴더>
        backend   = \\wsl.localhost\Ubuntu-24.04\home\<me>\projects\SimEngBay\backend
        workdir   = C:\simengbay\work\<앞두자>\<job-id>   (WSL 에선 /mnt/c/simengbay/work/…)
        결과      = <작업폴더>\.stage-<단계>.json   ← 부모는 **이 파일만** 믿는다
```

**경로를 명령줄에 싣는 이유**: WSL 에서 Windows 실행 파일을 부르면 환경변수가 건너가지 않는다
(`WSLENV` 에 적은 것만 간다). `PYTHONPATH` 를 주고 띄운 Windows 파이썬에서 그 값이 `None` 이었고
`-m app.core.run` 은 `No module named 'app'` 로 죽었다(실측 2026-09-20).

**`-X utf8` 인 이유**: 한국어 Windows 의 파이썬은 콘솔 코드페이지(cp949)로 찍는다. 그것을 UTF-8 로
읽던 부모가 `UnicodeDecodeError` 로 죽었다 — **단계는 성공했는데 워커가 터진다.**

| `.env` | 개발(지금) | 나중 — 플로팅 라이선스를 WSL 이 볼 때 | 운영(Apptainer 워커) |
| --- | --- | --- | --- |
| `SIMULATION_EXECUTOR` | `windows-bridge` | `local` | `local` |
| `WINDOWS_PYTHON` | `/mnt/c/simengbay/venv/Scripts/python.exe` | — | — |
| `WORK_DIR` | `/mnt/c/simengbay/work` (NTFS — Ansys 가 `\\wsl$` 에 쓰면 느리고 잠금 문제) | 아무 데나 | `/data/filestore/simulations` |
| Ansys | Windows 설치본 | WSL 에 리눅스 설치본 + `ANSYSLMD_LICENSE_FILE=1055@서버` | 호스트 `/ansys_inc` bind |

시험 · CI 는 `fake` 실행기(sleep + 모양만 맞는 산출물). 경로 변환은 `wslpath -w` 에게 묻는다 —
직접 바꾸면(`/mnt/c` → `C:`) 저장소가 WSL 파일시스템에 있을 때 틀린다. 솔브는 자식 프로세스
안에서 그 OS 의 MAPDL 을 직접 부른다(`ANSYS252.exe -b -np N -i model.dat`).

**개발 PC 환경 만들기**(한 번):

```bash
"/mnt/c/Python312/python.exe" -m venv 'C:\simengbay\venv'
/mnt/c/simengbay/venv/Scripts/python.exe -m pip install -r backend/requirements-worker.txt
# 확인 — 임베디드가 뜨고 라이선스를 받는가
/mnt/c/simengbay/venv/Scripts/python.exe -c "from ansys.mechanical.core import App; App(version=252).close(); print('ok')"
```

**첫날 확인한 것**(2026-09-20):
1. 임베디드 `App(version=252)` 이 이 라이선스로 **뜬다.** 원격 세션(`launch_mechanical`, gRPC)
   대안은 필요 없었다.
2. Student 판의 절점 상한에는 닿지 않았다(시험 형상 최대 1,976 절점). `mesh` 단계가 절점 수를
   요약에 실으므로 상한 근처인지 화면에서 보인다.
3. 약관 — 비상업. 개발 · 검증에만 쓰고 운영은 회사 라이선스(로드맵의 결정).

**아직 안 한 것**: 리눅스 `local` 실행기로 서버에서 한 번. **경로를 어떻게 주는지는 붙여
두었다**(2026-09-23) — 리눅스에서는 두 가지가 Windows 와 다르다:

| 무엇 | 왜 | 어디에 |
| --- | --- | --- |
| `AWP_ROOT<버전>` 환경변수 | **임베디드는 우리 명령줄 인자를 안 본다** — `App(version=…)` 은 스스로 이 이름을 찾는다. `.env` 의 `ANSYS_ROOT` 만 적으면 솔버는 찾고 모델링만 「Ansys 가 없다」 고 한다 | 워커 유닛이 `Environment=` 로 심고(`ANSYS_HOST_DIR` 를 준 경우), 실행기도 자식 환경에 같은 값을 넣는다 |
| `mechanical-env` 로 감싸기 | 리눅스 임베디드는 `LD_LIBRARY_PATH` 등이 맞아야 뜬다. Ansys 가 함께 깔아 주는 스크립트가 그것을 맞춘다 | `.env` 의 `MECHANICAL_ENV` — 비우면 맨 파이썬(Windows 는 그 스크립트가 없고 필요도 없다) |

**서버에서 처음 돌릴 때 확인할 것**: (1) `AWP_ROOT252` 가 컨테이너 안 경로를 가리키나
(호스트 경로를 심으면 컨테이너에 없다) · (2) `MECHANICAL_ENV` 없이 `App(version=252)` 가
뜨는가 — 뜨면 그 칸은 비워 둔다 · (3) 리눅스 임베디드가 같은 STEP 을 읽는가(리스크 1의
나머지 절반) · (4) PNG 는 OSMesa 가 있어야 나온다 — 없으면 VTP · 고유진동수만 나온다. 리스크 1 은 **Windows 임베디드에서는
해소됐고**(AutoJig STEP 이 그대로 들어온다), 리눅스 임베디드에서 같은지는 서버에서 확인한다.
